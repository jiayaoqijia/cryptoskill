# BalanceManager Move API

The `BalanceManager` is a shared object that stores balances across different assets and works with `TradeProof` objects to enable trading on pools. All interactions with DeepBook V3 require a BalanceManager except for direct swaps.

## Creating a BalanceManager

### Standard creation

```move
public fun new(ctx: &mut TxContext): BalanceManager
```

Creates a BalanceManager owned by the transaction sender.

### Custom owner

```move
public fun new_with_custom_owner(owner: address, ctx: &mut TxContext): BalanceManager
```

Creates a BalanceManager with a specified owner address.

### With capabilities

> **Deprecated:** `new_with_custom_owner_caps` is a deprecated stub (`abort 1337`). Use the `_v2` variant below.

```move
public fun new_with_custom_owner_caps_v2<App: drop>(
    _witness: App,
    deepbook_registry: &Registry,
    owner: address,
    ctx: &mut TxContext,
): (BalanceManager, DepositCap, WithdrawCap, TradeCap)
```

Creates a BalanceManager with an initial set of DepositCap, WithdrawCap, and TradeCap for the specified App type. Requires a witness of the `App` type and a reference to the DeepBook `Registry`.

## Authorization model

DeepBook uses a two-tier authorization model:

### Owner authorization

The BalanceManager owner has full control — deposit, withdraw, trade, stake, and manage capabilities. Owner authorization is proven via `generate_proof_as_owner`:

```move
public fun generate_proof_as_owner(
    balance_manager: &mut BalanceManager,
    ctx: &TxContext,
): TradeProof
```

This verifies that `ctx.sender()` matches the BalanceManager's owner address. The returned `TradeProof` authorizes all operations.

### Delegated authorization (TradeCap)

TradeCap holders can place orders and stake, but cannot deposit, withdraw, or manage capabilities:

```move
public fun generate_proof_as_trader(
    balance_manager: &mut BalanceManager,
    trade_cap: &TradeCap,
    ctx: &TxContext,
): TradeProof
```

This verifies that the TradeCap belongs to this BalanceManager. The returned `TradeProof` authorizes trading operations only.

## Capability management

Owners can mint up to 1,000 total capabilities per BalanceManager (combined across all cap types).

### Minting capabilities

```move
public fun mint_trade_cap(
    balance_manager: &mut BalanceManager,
    ctx: &TxContext,
): TradeCap
```

```move
public fun mint_deposit_cap(
    balance_manager: &mut BalanceManager,
    ctx: &TxContext,
): DepositCap
```

```move
public fun mint_withdraw_cap(
    balance_manager: &mut BalanceManager,
    ctx: &TxContext,
): WithdrawCap
```

All mint functions verify that the caller is the owner and that the total cap count is under 1,000.

### Revoking capabilities

```move
public fun revoke_trade_cap(
    balance_manager: &mut BalanceManager,
    trade_cap_id: ID,
    ctx: &TxContext,
)
```

`revoke_trade_cap` is the only revocation function. It can also be used to revoke a `DepositCap` or `WithdrawCap` by passing that cap's ID. Revocation removes the cap's ID from the BalanceManager's allowlist, making the cap object unusable.

## Deposits and withdrawals

### Depositing funds

Owner deposit:

```move
public fun deposit<T>(
    balance_manager: &mut BalanceManager,
    coin: Coin<T>,
    ctx: &TxContext,
)
```

Deposit via DepositCap (delegated):

```move
public fun deposit_with_cap<T>(
    balance_manager: &mut BalanceManager,
    deposit_cap: &DepositCap,
    coin: Coin<T>,
)
```

### Withdrawing funds

Owner withdrawal:

```move
public fun withdraw<T>(
    balance_manager: &mut BalanceManager,
    amount: u64,
    ctx: &mut TxContext,
): Coin<T>
```

Withdrawal via WithdrawCap (delegated):

```move
public fun withdraw_with_cap<T>(
    balance_manager: &mut BalanceManager,
    withdraw_cap: &WithdrawCap,
    amount: u64,
    ctx: &mut TxContext,
): Coin<T>
```

Withdrawals only access settled balances. Funds locked in resting orders cannot be withdrawn until those orders are canceled.

## Referral management

### Per-pool referrals

Each BalanceManager can be linked to a referral object for a specific pool. Referral owners earn a share of trading fees generated by the linked BalanceManager.

```move
public fun set_balance_manager_referral(
    balance_manager: &mut BalanceManager,
    referral: &DeepBookPoolReferral,
    trade_cap: &TradeCap,
)
```

```move
public fun unset_balance_manager_referral(
    balance_manager: &mut BalanceManager,
    pool_id: ID,
    trade_proof: &TradeProof,
)
```

## Events

- **`BalanceManagerEvent`** — emitted on BalanceManager creation
- **`BalanceEvent`** — emitted on deposits and withdrawals

## Typical integration patterns

### EOA-owned trading

```move
// In your contract or PTB:
let proof = balance_manager.generate_proof_as_owner(ctx);
pool.place_limit_order(
    balance_manager,
    &proof,
    client_order_id,
    0, // NO_RESTRICTION
    0, // SELF_MATCHING_ALLOWED
    price,
    quantity,
    true, // is_bid
    true, // pay_with_deep
    0,    // no expiration
    clock,
    ctx,
);
```

### Delegated trading via TradeCap

```move
// Trader holds a TradeCap, not the owner key
let proof = balance_manager.generate_proof_as_trader(&trade_cap, ctx);
pool.place_limit_order(
    balance_manager,
    &proof,
    // ... same parameters
);
```

### Protocol integration

A protocol can create a BalanceManager, hold the TradeCap internally, and allow users to trigger trades through the protocol's own access control:

```move
public fun protocol_trade(
    pool: &mut Pool<SUI, USDC>,
    balance_manager: &mut BalanceManager,
    trade_cap: &TradeCap,
    // ... user parameters
    ctx: &TxContext,
) {
    let proof = balance_manager.generate_proof_as_trader(trade_cap, ctx);
    pool.place_market_order(
        balance_manager,
        &proof,
        // ...
    );
}
```
