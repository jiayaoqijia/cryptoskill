# Idempotent activities

## Standard

An activity will sometimes run twice: a worker crashes after performing the effect but before recording it, a retry fires after a timeout that was actually a success, or a message is redelivered. Idempotency is what makes that harmless, and it requires an identifier the effect can be keyed on plus a store that records which identifiers have already been applied.

The identifier must be generated by the caller and carried with the request, not derived from the request's content. A hash of the payload is tempting but wrong: two legitimate identical payments would collide, and a retry with a slightly different timestamp would not. The caller knows whether it is retrying, so the caller is the only place that can supply the right key.

Primary sources: <https://aws.amazon.com/builders-library/> and <https://www.rfc-editor.org/rfc/rfc9110>.

## Decision rules

- Record the idempotency key: its source, scope, and lifetime.
- Record the store that records applied keys and its durability.
- Record the window over which a duplicate is detected, since a key that expires allows a late duplicate through.
- Record whether the key applies to the whole operation or to each effect within it.
- Record the response for a duplicate: the original result, an error, or a no-op.
- Record the cleanup of the key store, which otherwise grows without bound.

## Procedure

1. Identify each non-idempotent effect.
2. Assign a caller-generated key per effect.
3. Record the store and its durability.
4. Record the detection window and the duplicate response.
5. Record key expiry and cleanup.
6. Write the idempotency model per effect.

## Anti-patterns

- Deriving the key from the payload, which collides on legitimate duplicates.
- A key store that is not durable, so a crash loses the record.
- A detection window shorter than the maximum retry horizon.
- Returning an error for a duplicate, which makes the caller retry again.
- A key store with no cleanup, which becomes its own capacity problem.

## Done checklist

- [ ] Key source and scope recorded.
- [ ] Key store and durability recorded.
- [ ] Detection window recorded.
- [ ] Scope per operation or per effect recorded.
- [ ] Duplicate response recorded.
- [ ] Cleanup recorded.

The key's scope also needs to be decided per effect rather than per request: a workflow that charges and ships in one step needs two keys if either effect could be retried independently, and using one key for both means a retry after a partial success cannot tell which part already happened.
